Overview

theHarvester is a classic reconnaissance tool for the early stages of an authorized assessment: give it a domain or organization and it collects what the public internet already knows — hostnames, email addresses, IP addresses, URLs, ASNs, people’s names and breach names — normalized into one evidence set. The sources are search engines, certificate transparency logs, DNS datasets, code repositories and threat-intelligence platforms; a passive run never contacts the target itself.

Source tiers: P0 passive, P1 DNS, P2 direct

Sources are cataloged by how they behave. P0 passive sources need no API key and stay off the target’s infrastructure — crtsh, certspotter and commoncrawl are the safe defaults. P1 DNS and P2 direct sources require explicit selection because they resolve against or connect to the target. -b all runs the full P0 catalog; capability selectors like -b subdomains,emails pick every source that can produce what you care about. Three discovery sources run concurrently by default (-j adjusts the workers), and each source reports its own outcome — complete, partial with a reason, or zero findings — so the gaps in your evidence are visible, not silent.

More than a CLI

One engine now serves three interfaces: the CLI for one-off recon and shell pipelines, HarvestView — a local browser UI — for run history, evidence review, hostname change tracking and schedules, and a REST API on localhost for automation. Active add-ons extend a passive run when the engagement allows: DNS resolution (-r), subdomain brute force (-c), reverse DNS (-n), recursive DNS and subdomain-takeover checks.

How teams use it

Run it against your own domain before someone else does: the exposed webmail login, the forgotten staging host and the recruiting alias with a personal mailbox in its signature all show up in the output. Hand the subdomain list to DNS tooling, the email list to a breach check, the people list to your awareness program. Everything it gathers is already public — the skill is querying broadly and correlating the results, which is exactly what the tool automates. Free and open source (GPL-2.0), created by Christian Martorella and actively maintained.

Key features

  • Hostnames, emails, IPs, URLs, ASNs, people and breach names per domain
  • Keyless P0 sources: crtsh, certspotter, commoncrawl and more
  • Capability selectors: -b subdomains,emails,ips,asns,urls,people,breaches
  • Active add-ons: DNS resolution, brute force, reverse/recursive DNS, takeover checks
  • Three interfaces: CLI, HarvestView browser UI, REST API
  • Per-source outcome reporting — complete, partial or zero findings
  • Free and open source (GPL-2.0)

Install & first run

  1. theHarvester needs Python 3.14 and uv — the repo’s .python-version pins the interpreter automatically.
  2. Clone and sync: git clone https://github.com/laramies/theHarvester.git then cd theHarvester && uv sync.
  3. First run with two keyless P0 sources: uv run theHarvester -d example.com -b crtsh,certspotter.
  4. Widen it: -b subdomains for every subdomain-capable source, or -b all for the full P0 catalog.
  5. Read each source’s outcome in the terminal — zero-result and partial sources are reported, not hidden — then add opt-in P1/P2 sources only as the engagement allows.

Real-world example

You have just been authorized to test a company's public exposure. Start with theHarvester against their main domain: within minutes you hold a list of employee emails, subdomains and hostnames — the exact raw material an attacker would collect first.

Hand the subdomain list to your DNS checks and the email list to a breach lookup. Every forgotten staging host or exposed webmail login you find becomes a finding in the report, with the remediation advice to inventory subdomains and enforce multi-factor authentication on everything public.

Common questions

Is theHarvester free?

Yes — free and open source under GPL-2.0, created by Christian Martorella and maintained in the open. Everything runs locally; no account and no cloud service involved.

Which sources need an API key?

None of the P0 passive tier — crtsh, certspotter and commoncrawl among them run keyless. P1 DNS and P2 direct sources are opt-in because they touch the target’s infrastructure, and some third-party sources accept keys for deeper results. Start keyless: the P0 set already shows what is public.

Does it contact the target?

A passive run never contacts the target’s systems — but the project states the nuance honestly: the source providers still receive your query string. P1 DNS and P2 direct sources do touch the target, which is why they require explicit selection. For a quiet first pass, stay on P0.

How do I get only subdomains or only emails?

Use capability selectors: -b subdomains runs every source that can contribute subdomains, -b emails,urls unions those sets. Selectors decide which sources run; they do not filter the result types the sources return. --no-hosts drops hostname results when you want everything else.

Is the result set complete?

No — public sources are incomplete and stale by nature, and a shared per-source cap trims the largest result sets (--limit 0 lifts it; provider quotas still apply). Validate anything you report: resolve the host, confirm the mailbox, record where each fact came from.

theHarvester or SpiderFoot — which one?

SpiderFoot when you want a correlated entity graph from 200+ modules; theHarvester when you want a fast, honest passive sweep of emails, subdomains and people from one command. They stack well — run theHarvester first, feed its findings into everything else.

Is this legal to run?

Querying public indexes is ordinary OSINT, and the project’s own guidance is blunt: run it only against targets you own or have explicit permission to test. That permission is the line between a security assessment and unauthorized reconnaissance.
