## P0 — the sitemap is not dynamic (the headline finding)

### 1. `/sitemap.xml` is a stale static file, and it is the *wrong* one

Live query of the deployed site:

```text
GET https://password-e9a30.web.app/sitemap.xml
→ 200, <loc>https://oopsmypassword.com/checker.html</loc>
      <loc>https://oopsmypassword.com/blog.html</loc>
      <loc>https://oopsmypassword.com/guides/create-strong-password.html</loc>
```

Every URL in the served sitemap is a **legacy `.html` implementation URL**,
including `/blog.html` and `/guides/*.html` — paths that `firebase.json` has
since turned into 301 redirects. That file predates the pretty-URL rework.
Submitting it means asking crawlers to crawl redirect chains from a sitemap
that is months out of date.

### 2. Everything published from the admin panel is missing from it

Live Supabase (`GET /rest/v1/{articles,products}?status=eq.published`):

| Table | Published rows | In the live sitemap |
|---|---|---|
| `articles` | 2 (`cyber-security-salary-in-usa-…`, `langflow-cve-2026-0768-…`) | **0** |
| `products` | 1 (`master-in-ai-prompt`) | **0** |

A static, build-time sitemap can only ever list what existed at build time, so
this was structural, not a one-off omission.

### 3. The rewrite that was supposed to fix it was never deployed

```text
GET https://us-central1-password-e9a30.cloudfunctions.net/sitemap
→ 404 Page not found
```

`firebase.json` rewrites `/sitemap.xml` → the `sitemap` Cloud Function and lists
`sitemap.xml` in `hosting.ignore`. The function does not exist in the project.
The combination is the dangerous one: as soon as hosting *is* redeployed with
the current config, the stale file disappears and `/sitemap.xml` starts
returning **404** — worse than what it does today.

### 4. The static URLs were stamped with today's date on every request

`todayUtc()` was applied to all 35 static routes, so the whole sitemap appeared
to change daily. Crawlers learn to ignore a `lastmod` signal that never stops
moving, which throws away the one thing a dynamic sitemap is actually for.

### Fix — a real Supabase Edge Function

```
GET /sitemap.xml
  → Firebase Hosting rewrite            (sitemap.xml stays in hosting.ignore)
  → Firebase fn `sitemap`               (functions/index.js — bridge only)
  → Supabase Edge Function `sitemap`    (supabase/functions/sitemap/)
  → Supabase Postgres                   (published articles + products)
```

| File | Role |
|---|---|
| `supabase/functions/sitemap/index.ts` | Deno entry: env/secrets, CORS allowlist, degraded handling, `?format=json` |
| `supabase/functions/sitemap/sitemap-core.mjs` | route list, XML builder, escaping, slug filter, dedupe — **shared** |
| `functions/index.js` | rewritten as a thin bridge; no sitemap logic, no secrets |
| `functions/sitemap-core.mjs` | synced copy for the fallback (`npm run sync:sitemap`, also `predeploy`) |
| `tools/test_sitemap.js` | 15 tests, including "the two cores are byte-identical" |
| `assets/js/sitemap.js` | `/sitemap` (HTML) now lists live articles + products |

Properties now guaranteed:

- Published rows only — RLS **and** the generator both filter; drafts/archived can never appear.
- `lastmod` per row (`published_at` → `updated_at` → `created_at`); static pages keep a fixed build stamp.
- Slugs charset-guarded and XML-escaped *before* any URL is built (test: a
  `"><script>` slug is escaped, and parsing the output yields zero `script` elements).
- **Never 404s, never 500s** — Edge Function → REST fallback → static-only
  fallback, with `X-Sitemap-State` on the response so you can see which path served it.
- `tools/build.py` now parses `STATIC_ROUTES` / `STATIC_LASTMOD` out of the
  shared core, so even the committed snapshot cannot drift from the live one.

### ⚠️ Still needs a deploy (cannot be done from here)

## P0/P1 — admin panel

| # | Severity | Defect | Fix |
|---|---|---|---|
| A1 | **High** | `document_url` from the database was interpolated straight into `href="${esc(a.document_url)}"` in the article editor. `esc()` is HTML-escaping, **not** scheme validation — a row with `javascript:…` (or any row edited outside this panel) executed on click in an admin session. | New `documentHref()` gate uses the canonical `OMPUrl.safeUrl()`, same as `/articles`. Unsafe values render a red "unsafe URL — remove attachment" notice instead of a link. |
| A2 | Medium | One module-level `dirty` flag was shared by the article, product **and** tool forms. Opening a product form after touching an article inherited its state; saving one form cleared the other's. | `dirtyForms` Set keyed by form element; `setDirty` / `clearDirty` / `isDirty` / `hasUnsavedWork`. Detached forms are pruned so a cancelled editor can't keep blocking navigation. |
| A3 | Medium | `toolForm()`'s Cancel never reset `dirty` → the `beforeunload` "leave site?" guard stayed armed forever after one cancelled tool edit. | All three Cancel handlers now clear their own form's state and confirm before discarding. |
| A4 | Medium | The Edit button was disabled while loading and **never re-enabled** when the editor rendered. Cancelling the editor left a dead "Edit" button until the whole tab re-rendered. | `btn.disabled = false` after the row loads, before the form renders (articles, products, tools). |
| A5 | Medium | Saves never wrote `updated_at`, and the tables have no `UPDATE` trigger. The "sorted by updated_at" article list was really creation order, and the sitemap `<lastmod>` froze at publish time. | `updated_at` set explicitly on article and product saves, **plus** a `touch_updated_at()` trigger in the migration for edits made from anywhere else. |
| A6 | Medium | Deleting an article or product orphaned its Storage object (document / deliverable / cover) forever. | Delete reads the row first, then `removeStorageObjects()` after the delete succeeds (best-effort; logged, never thrown). |
| A7 | Medium | Replacing an attachment, cover or deliverable orphaned the previous object. | Orphans are collected when the new value is computed and removed only after the row write succeeds — a half-applied delete can't lose both files. |
| A8 | Low | The article list query was unbounded — every tab switch downloaded the whole table. | `.limit(ADMIN_ROW_LIMIT)` (300). |
| A9 | Low | The product cover preview accepted `data:` images (`allowDataImage: true`) while the save path rejected them — you could preview a cover that could never be published. | Preview uses the same rule as the save path (http(s) / site-relative only). |
| A10 | Low | The products list rendered `<img src="${esc(p.featured_image)}">` from the raw DB value. | Routed through the shared `safeHref()` gate. |
| A11 | Low | No `<noscript>`: with JS off the panel sat on "Loading secure admin panel…" forever. | `<noscript>` explains what happened. |
| A12 | Low | The Supabase SDK was imported as `https://esm.sh/@supabase/supabase-js@2` — a **floating major** from a third-party CDN, i.e. an un-reviewed, unpinnable code change to the admin panel. | Pinned to `@2.115.0` in `admin.js`, `articles.js` and `products.js`; a test asserts all three agree. |

## P1/P2 — Supabase security model (`supabase/00_schema_migrations.sql`)

| # | Severity | Defect | Fix |
|---|---|---|---|
| B1 | **High** | The `tools` table had **no admin write policies** — the file literally said *"Admin write policies omitted for brevity"*. ## Deliberate non-changes (flagged, not fixed)

1. **The production deploy is stale.** Evidence: the served `404.html` still
   links to `/checker.html` and `/sitemap.html`, and `/sitemap.xml` is the
   pre-rename version. `robots.txt` *is* current, so the deploy is partial/older
   than the repo. **Everything in this branch is invisible until
   `firebase deploy --only functions,hosting` runs** — and that deploy must
   include the Functions step, or `/sitemap.xml` will start 404ing.
2. **Blaze plan.** Firebase Cloud Functions need it. If you can't enable it,
   remove `"sitemap.xml"` from `hosting.ignore` so the committed snapshot is
   served again — it's accurate for static routes and merely incomplete for
   live content, which is strictly better than a 404.
3. **CSP still allows `style-src 'unsafe-inline'`** — thousands of inline
   `style=` attributes across generated pages. Removing it is a refactor, not a
   patch (unchanged from the previous audit).
4. **esm.sh remains a third-party runtime dependency.** Pinning removes the
   floating-version risk; it does not remove the supply-chain risk. The durable
   fix is vendoring `supabase-js` into `/assets/vendor/` (adds ~120 KB to the
   admin page only) and dropping `https://esm.sh` from `script-src`.
5. **Contact-form rate limiting is still client-side only** (a 12 s cooldown
   plus a honeypot). The migration still documents the server-side options;
   an Edge Function gate is the recommended next step.
6. **`/admin/` is publicly reachable.** That is by design — authentication and
   `profiles.is_admin` are enforced by Supabase Auth + RLS, and the page sends
   `noindex`. The panel is not a secret worth hiding; the database is.
