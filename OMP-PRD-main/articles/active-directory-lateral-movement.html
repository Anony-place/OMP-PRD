Active Directory Lateral Movement: Techniques and Detection

One compromised account should not become the whole domain. The lateral movement techniques attackers actually use in Active Directory - with the MITRE IDs…

Initial access is rarely the hard part of an intrusion. One phished laptop, one cracked password, one exposed service account - and the attacker is inside. What decides whether that foothold costs you one machine or the whole domain is lateral movement: the phase where an adversary walks from system to system using the credentials and trust your network already grants. In MITRE ATT&CK terms this is TA0008 - "the adversary is trying to move through your environment" - and in Active Directory it is where most ransomware incidents become catastrophic.

What lateral movement means - and what it is not

Lateral movement is horizontal: account to account, host to host, expanding the blast radius east-west across the network. It is distinct from privilege escalation (TA0004), which moves up - from a standard user to local administrator to domain admin. The two feed each other: a lateral hop often lands on a host where vertical escalation is possible, and the escalated account enables the next hop.

The structural problem in most Active Directory environments is simple: internal trust is flat. A workstation talks to a file server, which talks to a domain controller, and the same local administrator password - or the same over-privileged service account - quietly links them all. The techniques below exploit exactly that.

The six techniques attackers actually use

MITRE's Lateral Movement tactic lists nine techniques; six account for nearly everything seen in real incidents.

1. Pass-the-Hash (T1550.002)

NTLM authentication accepts the password hash itself as proof of identity. An attacker who dumps hashes - from memory, from a backup, from the SAM database - authenticates to other hosts without ever knowing the password. Tools: Impacket's psexec/wmiexec with -hashes, NetExec with -H, Mimikatz. It needs nothing but the hash and a reachable SMB or WinRM port.

2. Pass-the-Ticket (T1550.003)

The Kerberos twin of pass-the-hash: stolen or forged tickets (TGTs or service tickets) are injected and presented as legitimate authentication. From the defender's view the logon looks normal - it is a valid ticket - which is why ticket anomalies, not logon events, are the signal.

3. Remote services: SMB, RDP, WinRM, DCOM (T1021.*)

With valid credentials - stolen, cracked, or reused - attackers simply log in the way administrators do: the ADMIN$ and C$ shares over SMB (T1021.002), Remote Desktop (T1021.001), PowerShell remoting via WinRM (T1021.006), or DCOM object execution (T1021.003). Same tools as the helpdesk: PsExec, WMIExec, Evil-WinRM, mstsc. Legitimate protocols are the point - nothing to detect in the payload when there is no payload.

4. Service execution (T1569.002)

PsExec-style movement installs a small service on the target (PSEXESVC), runs the command, and removes it. The network traffic is ordinary SMB; the artifact is a service installation event and a named pipe. This is why "watch for new services" is a detection staple.

5. Kerberoasting (T1558.003)

The credential-access trick that feeds lateral movement - request service tickets, crack them offline, log in as the service account. Covered in detail below, because it is both common and quietly preventable.

6. Internal spearphishing and tool transfer (T1534, T1570)

Sometimes the movement is social: a compromised mailbox sends the "shared drive password" to the whole team. Sometimes it is logistics: the attacker copies their toolkit from host to host over SMB (T1570) to stage the next hop. Both leave trails - unusual senders internally, and file writes to admin shares.

Kerberoasting in the attack chain

Kerberoasting abuses a Kerberos design property: any authenticated domain user can request a Ticket Granting Service (TGS) ticket for any service registered with a Service Principal Name (SPN), and that ticket is encrypted with the service account's own password hash. When the ticket uses RC4 (encryption etype 23 - still negotiated in many environments), the result is an unsalted, unstretched hash that a GPU can chew through offline.

The whole attack is three steps, and the first two look like ordinary authentication:

# 1. Enumerate SPN accounts and request their TGS tickets
impacket-GetUserSPNs -request -dc-ip 10.10.10.10 CORP/user:Password

# 2. Crack the RC4 tickets offline (hashcat mode 13100)
hashcat -m 13100 tickets.txt rockyou.txt

# 3. Log in as the cracked service account - the lateral hop
netexec smb 10.10.10.0/24 -u svc_sql -p CrackedPassword123

Rubeus (Rubeus.exe kerberoast) and Metasploit's auxiliary/gather/get_user_spns do the same from a Windows foothold. A weak service-account password - the kind set once in 2019 and never rotated - often falls in minutes. And service accounts are gold: they run on servers, they hold local rights, and nobody puts them in the patching dashboard. The cracked account is exactly the kind of credential material that turns one host into many.

Detection. The tell is volume and type: Event ID 4769 (TGS requested) with Ticket Encryption Type 0x17 (RC4), one account requesting tickets for several different SPNs in a short window, especially from a workstation. Exclude machine accounts and the krbtgt service. PowerShell-based roasting also trips Script Block logging (Event 4104, KerberosRequestorSecurityToken).

Prevention. Group Managed Service Accounts (gMSA) remove the crackable password entirely; enforcing AES-only tickets removes the weak etype; 25+ character service passwords make offline cracking impractical; and the oldest fix of all - never put SPNs on privileged accounts. Our Kerberoasting glossary entry keeps the short reference version.

Detection: the event IDs that matter

Lateral movement is loud in the Windows Security log and quiet in the firewall. The baseline every AD defender should have forwarded to the SIEM:

Event IDWhat it showsWhat to look for
4624 (Type 3)Network logonOne account logoning onto many hosts in a short window
4624 (Type 10)Remote interactive (RDP) logonRDP from unusual sources, outside helpdesk hours
4625Failed logonSpraying patterns across many hosts
4648Logon with explicit credentialsThe pass-the-hash / runas fingerprint - a process supplying different credentials to a remote service
4672Special privileges assignedSpecial-privilege logons by non-admin accounts
4768 / 4769Kerberos TGT / TGS requested4769 bursts and RC4 (0x17) service tickets = Kerberoasting
4776NTLM credential validationNTLM use in a Kerberos-first environment
5140 / 5145Network share accessedADMIN$, C$ access from workstations that should not have it
7045New service installedPSEXESVC and friends - the service-execution signature
4688Process creationpsexec.exe, wmiexec.py, evil-winrm in the command line

The rules are boring on purpose: one-to-many relationship alerts (one account to many hosts; one host to many accounts), anomaly against a baseline, and correlation - 4648 followed by 7045 on the same target within minutes is nearly an incident report by itself.

Hardening that shrinks the blast radius

You cannot prevent every foothold. You can make the foothold worthless:

  • Unique local admin passwords. Windows LAPS (or the legacy LAPS) is the single highest-value control against pass-the-hash spread: a hash on one workstation stays on that workstation.
  • Tiered administration. Domain admin credentials never touch a workstation; admin workstations (PAWs) for tier-0 tasks. Most ransomware paths die at this boundary.
  • Credential Guard and Protected Users. Hashes stay out of LSASS memory; sensitive accounts cannot use NTLM or RC4 at all.
  • Retire RC4 and NTLM where you can. AES-only Kerberos closes the Kerberoasting window; NTLM restrictions kill pass-the-hash's easiest ride.
  • gMSA for every service. Automatic long passwords nobody knows and nobody needs to.
  • Segmentation and host firewalls. Workstations have no business opening SMB to the whole subnet. East-west filtering converts one compromised host from a domain problem into a helpdesk ticket.
  • Reduce local admins and monitor the shares. Every extra local admin is a hop; every ADMIN$ access is a log line you should be reading.

These are the same controls the security checklist tool tracks, and the same philosophy as secure remote access - verify the identity, limit the destination, watch the session.

Frequently asked

What is lateral movement in Active Directory?

The techniques an attacker uses to move from one compromised account or host to others inside the network - logging into remote services, reusing hashes and tickets, and abusing trust relationships - until they reach the systems they actually came for. MITRE ATT&CK catalogs it as tactic TA0008.

What is the difference between lateral movement and privilege escalation?

Lateral movement is horizontal (host to host, account to account, TA0008); privilege escalation is vertical (standard user to admin to domain admin, TA0004). In practice attackers alternate: escalate on one box, move to the next.

What is Kerberoasting in simple terms?

Any domain user can ask the domain controller for a service ticket, and that ticket is encrypted with the service account's password. Kerberoasting is requesting many such tickets and cracking them offline to recover service account passwords - MITRE T1558.003.

Which Windows Event ID detects lateral movement most often?

Event ID 4624 Type 3 (network logon) volume anomalies catch the most, with 4648 (explicit credential logon) as the strongest single indicator of hash or ticket reuse. For Kerberoasting specifically it is 4769 with RC4 encryption type 0x17.

How do you prevent lateral movement?

Remove the shared secrets that make it easy: unique local admin passwords (LAPS), tiered admin accounts, gMSA service accounts, AES-only Kerberos, reduced NTLM, and east-west network filtering. Detection on the event IDs above covers what remains.
