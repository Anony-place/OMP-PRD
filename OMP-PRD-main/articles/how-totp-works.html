How TOTP Works: The 30-Second Authenticator Code Explained

Every thirty seconds your authenticator app shows a fresh six-digit code. Nothing is pushed to your phone, no server is asked, and the code still works in airplane mode. That code is TOTP — the Time-based One-Time Password defined in RFC 6238 — and it is a surprisingly small piece of math: a keyed hash of the current time, truncated to six digits.

This article works the whole computation by hand with the RFC’s own test key, so the number you verify at the end is the official test vector. It also covers why the QR code you scan during enrollment is the credential, and what TOTP still cannot fix — real-time phishing.

How TOTP works: a worked example (RFC 6238)

TOTP is one line of math built on HMAC-SHA1. Your app and the server both hold the same shared secret K. Both compute the same counter from the current Unix time, and both derive the same code:

T   = floor((Unix time - T0) / X)     # X = 30 seconds by default, T0 = 0
TOTP(K) = HOTP(K, T) = Truncate(HMAC-SHA1(K, T)) mod 10^6

Take the RFC 6238 test key at Unix timestamp 59 — five seconds before the first code window expires:

Key       = "12345678901234567890"   (the RFC test secret, 20 ASCII bytes)
T         = floor(59 / 30) = 1
Counter   = 0000000000000001          (T as an 8-byte big-endian integer)
HMAC-SHA1 = 75a48a19d4cbe100644e8ac1397eea747a2d33ab
Offset    = last byte 0xab & 0x0f = 11
Bytes[11..14] = c1 39 7e ea
Masked    = 0x41397eea = 1,094,287,082
Code      = 1094287082 mod 1,000,000 = 287082

With eight digits instead of six, the same value gives 94287082 — the published RFC 6238 test vector for T = 59, so you can check this arithmetic against the standard itself. The dynamic truncation step — the last byte’s low nibble picks four bytes out of the twenty — is the same trick HOTP has used since RFC 4226.

TOTP vs HOTP: time versus counter

TOTP is HOTP with the counter replaced by the clock. HOTP (RFC 4226) counts events — its counter advances every time a code is generated — while TOTP counts 30-second time steps. The practical differences follow directly:

  • Expiry. HOTP codes stay valid until used; TOTP codes expire with their window, so an intercepted code becomes worthless within a minute.
  • Failure mode. HOTP desynchronises when a token generates codes nobody submits — servers heal that with a look-ahead window. TOTP’s failure mode is clock drift.
  • Server state. HOTP must track a counter per user; TOTP is stateless — the server only needs an accurate clock.

Almost every authenticator app today — Google Authenticator, Authy, 1Password, Aegis — speaks TOTP. HOTP survives mostly in older hardware tokens and offline scenarios where a device cannot keep time.

Why your code stops working: clock drift

Both sides compute floor(unix_time / 30). If your phone’s clock runs 31 seconds ahead of the server, you are a full step apart and the codes disagree. Servers therefore accept the previous and next steps too — a plus-or-minus one-step grace window covering 30–90 seconds of skew. Persistent failures mean the device clock is off by more than that: turn on automatic network time, and note that virtual machines and devices without a real-time clock drift fastest.

The QR code is the credential

Enrollment scans a QR code that encodes a URI like:

otpauth://totp/Example:you@example.com?secret=JBSWY3DPEHPK3PXP&issuer=Example

The secret parameter is the shared key itself, base32-encoded. Anyone who obtains it — a screenshot of the QR, an exported backup file, a cloud-synced authenticator account, an unencrypted phone backup — can generate every future code. Treat the QR and its secret exactly like a password: never screenshot it into your camera roll, prefer authenticators that store seeds encrypted or offline, and keep printed backup codes somewhere genuinely offline.

What TOTP cannot stop: real-time phishing

TOTP fixes what SMS 2FA gets wrong — no SIM-swap, no SS7 interception, no codes crossing the carrier network in cleartext — but it is not phishing-resistant. A phishing proxy that shows you the real login form can relay your code to the real site inside its 30-second window; this technique has been documented in real attacks since at least 2022, and NIST’s digital identity guidelines classify one-time passwords as not phishing-resistant for exactly this reason.

The hierarchy that follows:

  • Passkeys and hardware security keys — phishing-resistant (origin-bound), the right choice wherever they are offered.
  • A TOTP authenticator app — strong, portable and offline; the best widely available fallback.
  • SMS codes — still far better than a password alone; use where nothing else exists.

FAQ

Is TOTP the same as the code in Google Authenticator?

Yes. Google Authenticator, Authy, Microsoft Authenticator and most others implement TOTP (RFC 6238) behind the scenes: six digits, 30 seconds, HMAC-SHA1 over a per-account secret.

Can a code be reused inside the same 30 seconds?

Proper servers reject a code that has already been accepted (replay protection), but not all do. If a login fails oddly, waiting for the next window is the clean retry.

What happens if I lose my phone?

Without backup codes or an exported seed you lose the second factor entirely — this is what account-recovery flows are for. Print the backup codes at enrollment and store them offline; that single habit prevents almost every locked-out story.

A 60-second TOTP backup checklist

Losing the seed means losing the factor. Before you close the enrollment screen on your next account:

  • Save the backup codes. Print them or write them down; store them offline, not in the same password manager entry as the password.
  • Export the seeds deliberately, or not at all. If your authenticator offers encrypted export (Aegis, 1Password, Authy with a backup password), make the backup password strong and store the export offline. If it only offers plaintext export, skip it.
  • Prefer an authenticator with encrypted cloud backup for convenience accounts, and a local-only authenticator for high-value ones.
  • Test recovery once on a spare device: if the export has never restored, it is not a backup.
