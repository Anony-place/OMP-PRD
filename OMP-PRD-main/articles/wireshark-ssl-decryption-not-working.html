Wireshark SSL Decryption Not Working: Fix HTTPS, SSLKEYLOGFILE & Non-Standard Ports

Wireshark shows TLS as encrypted garbage or plain TCP? The fixes fail in a predictable order: dissection, key-log path, app key logging, captured handshake…

You set SSLKEYLOGFILE, pointed Wireshark at the file, and the HTTPS traffic still shows as encrypted Application Data — or worse, as raw TCP. The threads about this are old and scattered, and they rarely mention that the causes fail in a predictable order. This page walks that order, so you fix the layer that is actually broken instead of re-randomising settings.

1. Is Wireshark even treating the packets as TLS?

Before blaming decryption, check dissection. On a non-standard port (8088, 7777, a local dev server), Wireshark shows the stream as plain TCP payload and never even attempts TLS — so there is nothing to decrypt and no TLS section in the packet details.

  • Quick check: does the packet detail pane show a Transport Layer Security tree at all? If the payload shows only Data or TCP segment, this is your problem.
  • Fix: right-click a packet → Decode As → add your port as TLS (older menus say SSL). For a permanent fix, add the port to the TLS ports list in Preferences → Protocols → TLS (in some versions the list lives under Protocols → HTTP as "SSL/TLS ports").
  • Also confirm you are looking at the right traffic at all — if nothing is captured on your interface, start with our "No Interfaces Found" fixes and not-capturing-packets fixes first.

2. Wireshark needs the key log path — the variable alone is not enough

This is the single most common confusion. SSLKEYLOGFILE is read by the browser (or curl, or your TLS library), which then writes the session keys to that file. Wireshark does not read the environment variable. You must also tell Wireshark where the file is:

Edit - Preferences - Protocols - TLS
(Pre)-Master-Secret log filename:  C:\Users\you\keys.log     (Windows)
                                  /home/you/keys.log          (Linux/macOS)

Older Wireshark versions call this menu Protocols → SSL and the field "(Pre)-Master-Secret log filename" — same thing. After changing the path or growing the file, use View → Reload (Ctrl+R): on large captures Wireshark does not always pick up appended keys automatically.

3. Is the app actually writing keys?

If the key log file is empty or missing lines for the connection you captured, decryption can never work — the keys simply were never logged. The usual reasons:

  • The app started before the variable was set. Export SSLKEYLOGFILE first, then launch the browser — a running browser will not start logging retroactively.
  • Windows "protected" apps. UWP/Store apps and browsers running with Windows protection (AppContainer) cannot write the key log. Use the plain desktop build of Firefox or Chrome.
  • SChannel and some enterprise stacks. Apps doing TLS through Windows SChannel (many .NET and Windows-native programs) do not emit NSS-format key logs at all. Try the same site from Firefox or Chrome — if those decrypt, the app’s TLS stack is the difference.
  • Quick test: the file should gain new lines each time you load a page. No new lines = no keys = stop here and fix this first.

4. Is the full handshake inside the capture?

Wireshark can only decrypt a session when it has the matching key material and the handshake that the material belongs to:

  • Start the capture before you open the page. If you start capturing mid-session, the Client Hello (and its random value) is missing from the capture, and no key-log line can be matched to it.
  • Match the Client Random yourself: display filter tls.handshake.type == 1 to find the Client Hello, look at its Random field, and search that hex in your key log file. If no line matches, the keys for that session were not logged (cause 3) or belong to a different run.
  • Session resumption: a resumed handshake carries no fresh key exchange; it needs the original full handshake’s keys in the log. Reloading the page (Ctrl+F5) forces a fresh full handshake for the test.

5. The RSA private-key dead end

If your plan is "give Wireshark the server’s private key and it will decrypt": for any modern site this fails by design. Ephemeral Diffie-Hellman key exchange (DHE/ECDHE — what essentially every HTTPS site uses today, with Perfect Forward Secrecy) cannot be decrypted from the private key, even in principle. Wireshark’s RSA Keys list in the TLS preferences only works against old RSA key-exchange ciphers and TLS 1.2-era setups that still offer them. The answer is always the key-log route above — not the certificate.

6. Filters hiding the decrypted traffic (HTTP/2 and QUIC)

Decryption succeeded but "there is no HTTP" is often a display-filter problem:

  • After decryption, the HTTP layer sits inside the TLS stream. Filter http (or http2) to see the decrypted requests; filter tls to see the handshake and records. tls.handshake being green does not mean decryption failed.
  • HTTP/2 over TLS decrypts the same way; look for http2 frames after the key log is loaded.
  • HTTP/3 is QUIC — it runs over UDP 443, not TCP. If your filter is tcp.port == 443 you are looking at a different connection, or at nothing. Try udp.port == 443. The same key log works for QUIC decryption in current Wireshark versions.

The order, in one screen

1. Dissected as TLS at all?        -> Decode As / TLS ports list
2. Key log path set in Wireshark?  -> Preferences -> Protocols -> TLS
3. File gaining lines per page?    -> env var before app start; use desktop browser
4. Full handshake in the capture?  -> start capture first; match Client Random; Ctrl+F5
5. Trying the RSA private key?     -> dead end on PFS; use the key log
6. Decrypted but filtered out?     -> http / http2 filters; QUIC is UDP 443

FAQ

Why does decryption work for some sites but not others?

Almost always cause 3 or 4: the sites that work were loaded after the key log was configured, from an app that writes keys, with the capture already running. Each session needs its own line in the key log and its own handshake in the capture.

Do I need administrator rights to decrypt HTTPS?

You need capture privileges (see the interfaces guide) — decryption itself is just file-based: keys plus the capture, no elevated tricks.

Is decrypting HTTPS traffic something I am allowed to do?

On your own devices and in your own lab or authorised test scope, yes — that is the normal workflow for debugging and penetration testing. Decrypting other people’s traffic without authorisation is not.
