TruffleHog: Find, Verify and Analyze Leaked Credentials (2026 Guide)

TruffleHog is the open-source secrets scanner that finds API keys, passwords and private keys hiding in git history, chats, wikis and file shares — and tells you which ones are actually live. Here is how it works, how to run it, and where it fits next to Gitleaks.

Quick answer: TruffleHog (by Truffle Security) finds leaked credentials — what it calls secrets: a credential a machine uses to authenticate itself to another machine, including API keys, database passwords, private encryption keys, and more. Its differentiator is the pipeline after the find: it classifies 800+ secret types, validates whether each one is live, and analyzes the most-leaked types for owner, access and permissions. Free and open source (AGPL-3.0), 29.5k GitHub stars, actively developed (commits as recent as November 2026).

The four jobs TruffleHog does

The project frames its own capabilities as Discovery, Classification, Validation and Analysis — a useful checklist for any secrets-hygiene program:

1. Discovery — where it looks

TruffleHog scans Git, chats, wikis, logs, API testing platforms, object stores, filesystems and more. Practically: full git history (not just the latest commit), GitHub/GitLab orgs and repos, S3 buckets, GCS, filesystem trees, Docker images, and network shares. The git-history part is the classic win — secrets deleted in the latest commit are usually still sitting three commits back.

2. Classification — what it found

It classifies over 800 secret types, mapping them back to the specific identity they belong to — AWS key vs Stripe key vs Cloudflare token vs Postgres password vs SSL private key. This matters during triage: a generic regex match is noise; “this is an AWS access key for account X” is a ticket.

3. Validation — is it live?

For every secret TruffleHog can classify, it can also log in to confirm if that secret is live or not. This is the step that separates embarrassing-but-harmless findings (old rotated keys) from active incidents (a working production credential in a public repo). If you only remember one feature, make it this one.

4. Analysis — how bad is it?

For roughly twenty of the most commonly leaked credential types, TruffleHog goes beyond a login check: who created it, what resources it can access, and what permissions it has on those resources. That turns scanner output into an impact assessment — the same input your incident response or pentest report needs.

Install and first scan

All install routes are documented in the project repository:

# macOS
brew install trufflehog

# Docker
docker run --rm -it -v "$PWD:/pwd" trufflesecurity/trufflehog:latest github --repo https://github.com/trufflesecurity/test_keys

# install script (Linux)
curl -sSfL https://raw.githubusercontent.com/trufflesecurity/trufflehog/main/scripts/install.sh | sh -s -- -b /usr/local/bin

# from source
git clone https://github.com/trufflesecurity/trufflehog.git
cd trufflehog; go install

A first useful scan against a repo or an entire org looks like:

trufflehog github --repo https://github.com/your-org/your-repo
trufflehog github --org=your-org

Binary releases are also published on the GitHub releases page. Tip for triage runs: pipe the JSON output to a file and diff it between scans — the delta (new verified secrets) is your real work queue.

TruffleHog vs Gitleaks

Gitleaks is the other name in open-source secret scanning: rules-based regex scanning with a TOML rule set, fast and simple. The practical differences people cite:

  • Verification: TruffleHog validates findings against the provider (live or dead); Gitleaks reports matches and leaves verification to you.
  • Classification: TruffleHog’s 800+ typed detectors vs regex rules.
  • Sources: TruffleHog reaches beyond git (object stores, chat platforms via enterprise); Gitleaks is git/file-centric.
  • License: TruffleHog is AGPL-3.0; Gitleaks is MIT — some legal teams care about this for internal tooling.

They are complementary in practice: many teams run Gitleaks as a fast pre-commit/CI gate and TruffleHog for deeper sweeps and incident triage. The head-to-head lives on our TruffleHog vs Gitleaks comparison page, and Gitleaks has its own tool page.

Where TruffleHog fits in a security program

  • Pre-commit and CI: catch secrets before they reach the remote. A failed pipeline on a verified secret is a cheap control.
  • Incident response: the first command when a repo goes public or an employee leaves — what credentials were exposed, and are they live?
  • Pentest deliverables: exposed-credential findings are among the highest-severity items in reports; TruffleHog output (classification + validation evidence) drops straight into the findings section of our pentest report template.
  • M&A and vendor audits: scanning a codebase or share you are about to inherit answers what will we own?
  • Continuous monitoring: the enterprise product continuously monitors Git, Jira, Slack, Confluence, Teams and SharePoint (the paid product funds the open-source development, per the project README).

The workflow that actually works

Finding secrets is easy; the program is the hard part:

  1. Scan broadly (org-wide, full history) and triage verified findings first — live credentials are incidents, not tickets.
  2. Rotate before you clean. Removing the secret from git does nothing; the credential is still valid. Rotate/revoke, then clean history.
  3. Classify the blast radius (TruffleHog’s analysis step does this for common types): which account, which resources, which permissions.
  4. Prevent the next one: pre-commit hooks, CI gates, secret managers, short-lived credentials.
  5. Document — for audits and report deliverables, keep the finding, the validation evidence, and the rotation proof together.

FAQ

Is TruffleHog legal to run?
On your own repositories, shares and infrastructure: yes — that is what it is for. Scanning systems you do not own or are not authorized to test is a different matter entirely; get written authorization first.

Does it really check whether a key works?
Yes — for the secret types it can classify, it can attempt authentication to confirm whether the credential is live. That validation step is the product’s core value.

What about false positives?
Every regex scanner has them; TruffleHog’s validation step exists precisely to sort real-live secrets from inert strings. Always confirm scope before rotating anything in production.

Is it free?
The scanner is open source under AGPL-3.0. Truffle Security sells an enterprise monitoring product; the README states that revenue funds the open-source work.

Can it scan private/internal systems?
Git remotes, filesystems and object stores you can authenticate to — yes. Chat platforms and SaaS sources are covered in the enterprise tier.

TruffleHog vs GitLeaks — which one?
Run both at different layers: Gitleaks for a fast git gate, TruffleHog for validated deep scans. The comparison page breaks it down.
