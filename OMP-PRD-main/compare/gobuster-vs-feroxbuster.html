Gobuster vs Feroxbuster: Content Discovery Compared

Compare Gobuster and Feroxbuster for directory and content discovery: recursion, wildcard filtering, extension handling, link extraction, speed and where each one fits in a web assessment.

Short answer: Gobuster is the dependable default for a fast, single-purpose sweep, and it is the only one of the two with DNS, vhost and cloud-bucket modes. Feroxbuster is the better choice when the target is a single application you expect to be deep - it recurses, filters soft-404s automatically and harvests new paths from the responses it already received.

Executive Verdict: When to Choose Each

Choose Gobuster if…

Best for breadth: dedicated dir, dns, vhost, fuzz, s3 and gcs modes, a tiny memory footprint, and output that is easy to diff between runs. Reach for it when you need the whole hostname or DNS surface, not one site.

Choose Feroxbuster if…

Best for depth: recursive by default, auto-calibrated against wildcard responses, extension-aware, able to resume an interrupted scan, and it extracts links from the pages it has already fetched.

Recursion is the real fork in the road

The first request finds /admin/. The interesting question is what sits behind it. Gobuster has no answer to that on its own: it reports /admin/ and moves on, and finding /admin/backup/ means running the whole wordlist again with a different URL, for every directory you find. Scripting that loop by hand is where most people first reach for a different tool.

Feroxbuster treats recursion as the normal case. Give it a URL and a wordlist and it keeps going: every directory it discovers becomes a new base for the same wordlist, until --depth is reached. A single command therefore covers a tree that would otherwise need a shell loop with bookkeeping, and it keeps a state file so a scan interrupted by a network drop can continue rather than restart.

The cost is traffic. Recursion multiplies the number of requests by the number of directories found, and an application with twenty nested paths is suddenly a five-figure request count. On a production target that is exactly the volume that gets you noticed, or rate-limited, or asked to stop. Set --rate-limit and --time-limit before you start, not after.

Wildcard responses will ruin your results

Many modern applications answer 200 to everything, serving a friendly "page not found" page with the same layout for any path you invent. A scanner that trusts the status code reports every single word in the wordlist as a hit. The report is not just noisy - it is useless, because the one real directory is somewhere in nine thousand identical lines.

The fix is calibration: request a handful of paths that almost certainly do not exist, record the shape of the response (status, length, word count, line count), and treat anything matching that shape as noise. Gobuster makes you do this by hand - notice the length of a random path, then pass --exclude-length. It works, and it is fast once you know the number.

Feroxbuster measures it for you before the scan starts, and --autotune re-checks periodically because some servers answer differently once you send real traffic. This is the single biggest practical difference between the two, and it is why an unattended overnight scan is a Feroxbuster job.

Gobuster is not only a directory tool

The comparison usually stops at directories, which undersells Gobuster. Its dns mode resolves subdomains against a resolver, vhost mode probes the Host header while keeping the same IP, and the s3 and gcs modes check bucket names on cloud storage endpoints. Feroxbuster has no equivalent: it is an HTTP content discovery tool and does not speak DNS or talk to bucket APIs.

In a real assessment the two are used one after the other. Gobuster vhost and dns modes map the host surface; Feroxbuster crawls the applications that surface. Choosing between them only matters if you were going to install just one, and the honest answer there is Gobuster, because it covers more ground before you know what the target looks like.

Side-by-Side CLI & Operational Workflow

Gobuster Example

# Directory sweep, excluding a known 4242-byte soft-404 page
gobuster dir -u https://target.example.com -w /usr/share/seclists/Discovery/Web-Content/common.txt -x php,html,js -b 404,403 --exclude-length 4242 -t 30

# Virtual host discovery on the same IP
gobuster vhost -u https://target.example.com -w subdomains.txt --append-domain

Feroxbuster Example

# Recursive crawl with automatic wildcard calibration and a request ceiling
feroxbuster -u https://target.example.com -w /usr/share/seclists/Discovery/Web-Content/raft-medium-directories.txt -x php,html,js --depth 3 --rate-limit 80 --time-limit 30m --extract-links

# Continue an interrupted scan where it stopped
feroxbuster --resume-from ferox-1717440000.state

Frequently Asked Questions

Is Feroxbuster always better than Gobuster?

No. Feroxbuster is better at one job - deep, recursive HTTP content discovery - and does not do DNS enumeration, virtual host discovery or cloud bucket checks at all. If you are mapping an unknown host, Gobuster covers four of those surfaces and Feroxbuster covers one.

Which one is faster?

They are close enough that the answer depends on your settings, not the tool: thread count, rate limits, wordlist size and whether recursion is on all matter more than the language they are written in. A recursive Feroxbuster run sends far more requests than a flat Gobuster run, so raw speed comparisons between the two are usually comparing different amounts of work.

Can they share wordlists?

Yes, and they should. Both read a plain newline-delimited wordlist, so the SecLists collections work unchanged: Wordlists like common.txt or raft-medium-directories.txt are the usual starting points. A custom wordlist built from the target technology stack will outperform any generic list with either tool.

Why does Gobuster report every word as found?

The application is answering 200 to paths that do not exist. Pick a random string that is certain not to exist, request it, note the response length, and pass that number to --exclude-length. If the length varies slightly per request, add a second exclusion for line count or switch to a tool that calibrates automatically.

Is content discovery legal without permission?

No. Directory brute-forcing sends thousands of unsolicited requests to a system, which is unauthorised access in most jurisdictions regardless of whether anything is exploited. Run these tools only against systems you own, your own lab, or a target with written authorisation that defines the scope and the allowed request rate.
