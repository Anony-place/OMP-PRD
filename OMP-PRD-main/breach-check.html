Breach Check

Learn how privacy-preserving breach lookup works — and try a transparent local demo. This page is not connected to a live breach database, and never claims to be.

Try the demo lookup

Type any password. It is SHA-1-hashed locally; only the first 5 hash characters are compared against a tiny built-in demo corpus of known-compromised passwords. Nothing is transmitted.

Demo limitations. The built-in corpus contains only ~330 famous compromised passwords. "Not found" proves nothing. A production version would use a licensed breach-data API with k-anonymity range queries — and this page would say so explicitly.

What is a breach?

When a service is compromised, its user database — emails, password hashes, personal details — can be stolen and later published or sold. Billions of such records circulate in "combo lists" used for credential stuffing.

Why reuse is the real danger

Attackers don't need to hack your bank — they take a password leaked from a breached forum and replay it everywhere you have an account. Unique passwords turn a breach into a one-account problem.

The model

How k-anonymity breach lookup works

The same architecture used by services like Have I Been Pwned's Pwned Passwords range API.

Hash locally

Your password is hashed on your device (e.g., SHA-1, as the range API standard uses). The password itself never leaves the browser.

Send only a prefix

Only the first 5 characters of the hash are sent to the API — a "range" shared by hundreds of unrelated hashes. The service cannot tell which password you meant.

Match locally

The API returns all hash suffixes in that range; your device compares locally. Full hash and password stay with you — anonymity set: everyone sharing the prefix.

Where OMP is going: this demo is built behind a clean BreachProvider-style interface, so a real k-anonymity range API can be connected later without changing the UI — with explicit consent, documented in our privacy policy before any network call ships.

Why hashing alone doesn't make passwords safe

It is tempting to think "hash it and it's protected". Reality is harsher:

  • Fast hashes are brute-forceable. MD5/SHA-1 are designed for speed; a modern GPU rig tries ~10¹¹ candidates per second against leaked databases.
  • Unsalted hashes leak equality. Identical passwords produce identical hashes, enabling rainbow tables and instant matches across users.
  • Hashing is not encryption. It is one-way only against inputs with enough entropy — human passwords usually don't have it, which is exactly what cracking exploits.
  • The fix is layered: salted, memory-hard hashing (Argon2/bcrypt) on the server side; unique, generated passwords and 2FA on yours.

If a service you use was breached, follow the playbook in What to Do After a Data Breach.
